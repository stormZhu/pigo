# pigo 接口契约全景地图

> 范围：仓库内所有**具名 Go 接口**（`type X interface {...}`）及其实现者，按 package 分类。
> 统计基线：`internal/` + `agent/` 共 **16 个具名接口**，分布在 **8 个 package**；生产实现者 **40+ 个**，另有若干测试替身（test stub）。
> 方法：`grep -n 'interface\s*{' --include=*.go` 全量枚举，再按 `isXxx()` marker / 导出方法集反查实现者。

## 二、分层与依赖方向

依赖只向下流动（`agentcore` 是叶子层，不 import 任何业务包）：

```
                       ┌──────────────────────────────┐
        agent (SDK)    │  Event 🔒                     │
                       └──────────────┬───────────────┘
                                      │
   ┌──────────────────────────────────┼───────────────────────────────┐
   │                                  ▼                               │
   │                    provider: AssistantMessageEvent 🔒             │
   │                              Provider 🔓  Decoder 🔓              │
   │                                  ▲                               │
   │     runtime: ReminderProvider 🔓 │  agenttool: searchBackend 🔓   │
   │     AgentTool 的实现遍布 runtime / agenttool / plugin / agent       │
   └──────────────────────────────────┬───────────────────────────────┘
                                      ▼
        ┌───────────────────────────────────────────────────────┐
        │  agentcore (叶子层):                                   │
        │    Content 🔒  Message 🔒  AgentEvent 🔒  AgentTool 🔓 │
        └───────────────────────────────────────────────────────┘
```

上层 `cli`（`Host` / `Editor`）、`dream`（`SessionSource` / `Consolidator`）、`remotecontrol`（`Sink` / `Handler`）是**应用装配层的接缝**，互不依赖，只向下依赖核心层。

## 三、事件双层抽象：`AgentEvent` 与 `AssistantMessageEvent` 的层级关系

上文「分层与依赖方向」图中，`agentcore` 与 `provider` 各有一个密封事件接口，二者名字相近，却是全仓**最容易混淆的一对契约**——它们分属两个抽象层级，前者消费并包装后者。

### 3.1 一句话定位

- `AssistantMessageEvent`（provider 层，**低层**）：**单次 LLM 流式响应的增量事件**。
- `AgentEvent`（agentcore 层，**高层**）：**整个 agent 循环的运行时事件**（跨多 turn、多消息，涵盖工具执行 / 压缩 / 遥测）。

### 3.2 对比

| 维度   | `AssistantMessageEvent`                               | `AgentEvent`                       |
| ---- | ----------------------------------------------------- | ---------------------------------- |
| 定义   | provider.go:21                                        | event.go:6                         |
| 所在层  | `provider`（依赖 agentcore）                              | `agentcore`（零依赖叶子层）                |
| 判别方法 | `EventKind() string`                                  | `EventType() string`               |
| 成员数  | 6                                                     | 14                                 |
| 生命周期 | 一条 assistant 消息的流式过程                                  | 一次 loop run 全程                     |
| 产生者  | 具体 provider driver / `Decoder`（SSE 解析）                | agent loop（`runtime`）              |
| 消费者  | loop 的 `streamAssistantResponse`（聚合增量）                | UI / TUI / headless、插件通知、telemetry |
| 终止语义 | 有统一终止事件（`done` / `error`），驱动 `EventStream.IsComplete` | 无统一终止事件，靠 `agent_end` 界定 run 结束    |
| 载荷   | `Partial` / `Message` 消息快照 + `Err`                    | 消息、工具结果、token 计数等业务载荷              |

### 3.3 数据流：低层增量 → 高层事件

```
provider driver / Decoder
  └─ 产出 AssistantMessageEvent(start → text/thinking/toolcall… → done|error)
       └─ loop 将其累积成 AgentMessage 快照
            └─ 包装为 AgentEvent(message_start / message_update / message_end …)
                 └─ 原始事件经 MessageUpdateEvent.AssistantMessageEvent 透传给消费者
```

### 3.4 关键设计点：为什么透传字段是 `any`

`MessageUpdateEvent` 会把产生该增量的原始 provider 事件**原样透传**（event.go:62-65），但字段类型是 `any`，而非 `AssistantMessageEvent`：

```go
type MessageUpdateEvent struct {
    Message               AgentMessage
    AssistantMessageEvent any
}
```

原因是 **`agentcore`** **不能反向 import** **`provider`**（叶子层零依赖约束）。若此处直接写成 provider 的具体类型，就会形成 `agentcore → provider` 的反向依赖并成环。故用 `any` 做类型擦除，把「如何解释这个原始事件」的责任交给上层消费者。

### 3.5 第三层：`agent.Event`（公开 SDK 投影）

公开 `agent` 包的 `Event`（events.go:25，7 个成员）是 `AgentEvent` 面向 SDK 消费者的**精简投影**：只暴露文本 / 推理增量、工具执行与用量，屏蔽 loop 内部生命周期（agent / turn / compaction / telemetry）。三层关系：

```
AssistantMessageEvent  (provider,   6 个)  单条消息的线格式增量
        ↑ 聚合
AgentEvent             (agentcore, 14 个)  loop 运行时全量事件
        ↑ 投影
agent.Event            (agent,      7 个)  对外 SDK 的稳定子集
```

## 五、两类设计范式小结

| 范式         | 特征                                             | 代表接口                                                                                                                                | 用途                            |
| ---------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| **密封判别联合** | 未导出 marker + 判别字符串；消费端 `type switch`；JSON 手工派发 | `Content` `Message` `AgentEvent` `AssistantMessageEvent` `Event`                                                                    | 表达「封闭取值集合」，新增成员必须改本包，杜绝外部伪造分支 |
| **开放式接缝**  | 全导出方法集；依赖倒置 / 依赖注入                             | `AgentTool` `Provider` `Decoder` `ReminderProvider` `Host` `Editor` `Sink` `Handler` `SessionSource` `Consolidator` `searchBackend` | 表达「能力契约」，实现可无限扩展、便于测试替身替换     |

> 注：`searchBackend` 虽是未导出名字，但**没有 marker**，属开放式（仅限包内可见，非密封语义）。

## 六、维护提示：如何增量核对

```bash
# 1. 枚举全部具名接口
grep -rn --include=*.go -E '^\s*type\s+\w+\s+interface\s*\{' . | grep -v _test.go

# 2. 密封接口：按 marker 反查实现者
grep -rn --include=*.go -E 'func \([^)]*\) (isContent|isMessage|isAgentEvent|isAssistantMessageEvent|isEvent)\(\)' .

# 3. 开放接口：按关键方法反查实现者，例如 AgentTool / Provider / Decoder
grep -rn --include=*.go -E 'func \([^)]*\) ExecutionMode\(\) agentcore\.ToolExecutionMode' .
grep -rn --include=*.go -E 'func \([^)]*\) StreamCompletion\(' .
grep -rn --include=*.go -E 'func \([^)]*\) Decode\(payload \[\]byte\)' .
```

新增接口时请同步更新本文件「总览表」与对应 package 小节。
