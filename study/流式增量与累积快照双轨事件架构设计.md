# 流式增量与累积快照双轨事件架构设计

本笔记深入剖析 `pigo` 在大模型流式输出（Streaming）中，事件层 `MessageUpdateEvent` 采用的 **“累积快照（Cumulative Snapshot）+ 底层增量（Raw Delta）”** 双轨封装哲学。重点解析 **为什么不采用单一增量或单一快照**、**UI 渲染层（TUI/Web）与流控分发层（SDK/Pipeline）的异构消费诉求**、**如何避免重复 diff 计算与状态机复杂性**，以及 **运行时的组装时序与数据流向**。

## 一、核心结构定义与问题背景

在配套电子书 [`book/chapter2.md:382-391`](file:///Users/yuqing/Documents/workspace/pigo/book/chapter2.md#L382-L391) 中有这样一段关键论述：

> `Message` 是"当前累积的部分消息"，`AssistantMessageEvent` 是"产生这次增量的那个 Provider 级原始事件"——渲染层既能拿累积态刷新画面，也能触到底层增量做精细控制。

对应的 Go 结构体定义在 [`internal/agentcore/event.go`](file:///Users/yuqing/Documents/workspace/pigo/internal/agentcore/event.go#L60-L65)：

```go
// MessageUpdateEvent is emitted for each streaming delta, carrying the current
// partial message and the raw provider-level event that produced it.
type MessageUpdateEvent struct {
	Message               AgentMessage // 当前累积的局部消息（通常为 AssistantMessage 快照）
	AssistantMessageEvent any          // 产生这次增量的 Provider 级原始事件
}
```

在大模型交互中，LLM 输出是一个持续数秒乃至数分钟的流式序列（Streaming Tokens）。每次网络层面收到一个分块（Chunk），系统就会向外派发一个 `MessageUpdateEvent`。

这里引发了一个深刻的架构设计问题：**既然是事件驱动架构，为什么不单纯发送刚刚到达的增量（Delta），也不单纯发送最新拼装好的快照（Snapshot），而是选择同时打包这两个字段？**

## 二、单轨设计的致命困境：为什么不二选一？

### 1. 方案 A：仅提供底层增量（Delta-only）的痛点

许多初期的流式 API 或框架只通知新字符，例如：`OnDelta(token string)`。

```
LLM Chunk ──> Event: { Delta: " world" }
```

**消费者之痛**：
1. **渲染端负担过重**：终端全屏 UI、Web 前端或 Markdown 渲染器是按“块”工作的。一个 Markdown 的代码块（如 ````go ... ````）或者粗体文本，在流式接收时，必须等完整的闭合标签到达才能完成语法树解析与高亮。如果只有 Delta，**每一个消费端都必须在本地维护一个字符串缓冲区（Buffer）和解析状态机**。
2. **多模态与复合内容组装极其复杂**：现代大模型的回复混杂了多种类型（思考块 Thinking、正文文本 Text、工具调用 ToolCall、参数 JSON 片段）。仅靠增量，消费端需要自行处理“当前增量属于哪一个工具调用参数”、“当前是不是思考过程”等复杂的上下文拼装，极易导致不同端实现的 Bug 与行为不一致。

### 2. 方案 B：仅提供累积快照（Snapshot-only）的痛点

有些框架为了简化消费端，选择只提供当前已累计的完整文本，例如：`OnUpdate(fullMessage Message)`。

```
LLM Chunk ──> Event: { Message: "Hello world" }
```

**消费者之痛**：
1. **流式追加输出开销剧增（$O(N)$ 前缀比对）**：如果消费端是一个最朴素的终端 stdout 打印机（打字机效果），它不需要清屏重绘，只需要把“新出来的几个字”打印出来。如果只有 `Message`，消费端**每次收到更新都必须拿当前完整字符串与上一帧的字符串做 diff 比对**（求公共前缀并截取后缀）。当文本输出达到数万字时，频繁的字符串截取和前缀匹配会产生严重的内存分配与无谓的 CPU 浪费。
2. **语义丢失（Semantic Loss）**：大模型如果在同一轮中先后输出了思考（Thinking）和正文（Text），单看快照，消费端很难一眼判断“刚刚这一瞬间，到底是思考推进了几个字，还是正文推进了几个字”，除非比对各个 Block 的版本号或长度。

## 三、双轨架构设计：各取所需的优雅解耦

`pigo` 采用的双轨设计（Dual-Track Pattern），直接将**累积态**与**动作者**绑在同一个载体上，实现了消费端的彻底解耦与自由选择。

```
               ┌────────────────────────────────────────────────────────┐
               │                  MessageUpdateEvent                    │
               │                                                        │
               │  Message:               AssistantMessage (完整快照)    │
               │  AssistantMessageEvent: provider.StreamTextEvent (原始)│
               └───────────────────────┬────────────────────────────────┘
                                       │
                ┌──────────────────────┴──────────────────────┐
                ▼                                             ▼
     【路径 A：累积态快照刷新】                    【路径 B：底层增量精细控制】
   适用场景：TUI 重绘、富文本渲染               适用场景：Stdout 流式追加、多通道分发
   消费字段：e.Message                          消费字段：e.AssistantMessageEvent
   优势：0 拼接逻辑，直接全量渲染                优势：0 Diff 开销，明确增量意图
```

### 1. 轨道一：面向声明式渲染与重绘的 Message 快照

在交互式终端或图形界面中，采用类似 React / Elm 的声明式渲染范式。在 [`internal/runtime/render.go:60-64`](file:///Users/yuqing/Documents/workspace/pigo/internal/runtime/render.go#L60-L64) 中：

```go
case agentcore.MessageUpdateEvent:
    if a, ok := e.Message.(agentcore.AssistantMessage); ok {
        emitText(agentcore.ContentToText(a.Content))
    }
```

渲染器直接使用 `e.Message` 提取当前完整的文本内容。消费端不需要关心底层模型经历了多少次分片、协议是 Anthropic 还是 OpenAI，只要拿 `e.Message` 喂给 Markdown 渲染组件，即可完成整个区域的平滑刷新。

### 2. 轨道二：面向精细控制与多通道分流的 AssistantMessageEvent

`AssistantMessageEvent` 在 [`internal/provider/provider.go:18-58`](file:///Users/yuqing/Documents/workspace/pigo/internal/provider/provider.go#L18-L58) 中定义了一组密封的判别类型：

```go
type AssistantMessageEvent interface {
    isAssistantMessageEvent()
    EventKind() string
}

// 具体增量子类型：
type StreamStartEvent    struct{ Partial agentcore.AssistantMessage }
type StreamTextEvent     struct{ Partial agentcore.AssistantMessage }
type StreamThinkingEvent struct{ Partial agentcore.AssistantMessage }
type StreamToolCallEvent struct{ Partial agentcore.AssistantMessage }
type StreamDoneEvent     struct{ Message agentcore.AssistantMessage }
type StreamErrorEvent    struct{ Message agentcore.AssistantMessage; Err error }
```

消费端通过类型断言（Type Switch），可以不费吹灰之力进行精细通道分流：
- **`StreamThinkingEvent`**：模型正在输出思维链，将其路由到顶部的折叠面板或以暗灰色字体渲染。
- **`StreamTextEvent`**：模型正式回复正文，以高亮终端字体直接流式打印。
- **`StreamToolCallEvent`**：模型正在组装函数调用的 JSON 参数，此时界面展示加载中动画（Spinner），告知用户正在组织工具调用。

### 3. 轨道三：SDK 事件映射中的双游标前缀差量算法

在供第三方调用的公共 SDK [`agent/events.go:154-178`](file:///Users/yuqing/Documents/workspace/pigo/agent/events.go#L154-L178) 中，`eventMapper` 巧妙结合两者，利用双游标（`previousText` 与 `previousThinking`）将内部复杂事件优雅降维为对外部开发者最友好的 `MessageDeltaEvent` 与 `ThinkingDeltaEvent`：

```go
func (m *eventMapper) handleMessageUpdate(message agentcore.AssistantMessage) {
    currentText, currentThinking := assistantStreams(message.Content)
    textSkip := sharedPrefixLength(m.previousText, currentText)
    thinkingSkip := sharedPrefixLength(m.previousThinking, currentThinking)

    for _, block := range message.Content {
        switch value := block.(type) {
        case agentcore.TextContent:
            delta, remaining := contentBlockDelta(value.Text, textSkip)
            textSkip = remaining
            if delta != "" {
                m.emitEvent(MessageDeltaEvent{Text: delta}) // 发出纯文本增量
            }
        case agentcore.ThinkingContent:
            delta, remaining := contentBlockDelta(value.Thinking, thinkingSkip)
            thinkingSkip = remaining
            if delta != "" {
                m.emitEvent(ThinkingDeltaEvent{Text: delta}) // 发出思维链增量
            }
        }
    }

    m.previousText = currentText
    m.previousThinking = currentThinking
}
```

SDK 外部调用方既可以监听整体快照，也可以只监听纯净的增量事件，底层机制浑然一体。

## 四、完整数据链路：从 Provider Chunk 到事件消费

以下序列图还原了从底层网络 Chunk 到最终双轨事件派发的完整生命周期：

```
LLM Server        Provider          Runtime (stream_response)        Render / Consumer
    │                 │                         │                            │
    │── HTTP Chunk ──>│                         │                            │
    │                 │ (反序列化为增量)           │                            │
    │                 │── StreamTextEvent ─────>│                            │
    │                 │                         │                            │
    │                 │                         │ 1. backfill(e.Partial)     │
    │                 │                         │    更新本地累积快照         │
    │                 │                         │                            │
    │                 │                         │ 2. 组装双轨事件:            │
    │                 │                         │    MessageUpdateEvent {    │
    │                 │                         │      Message: 累积快照,    │
    │                 │                         │      AssistantMessageEvent │
    │                 │                         │    }                       │
    │                 │                         │                            │
    │                 │                         │── MessageUpdateEvent ─────>│
    │                 │                         │                            │
    │                 │                         │                            │ 3. 消费端各取所需:
    │                 │                         │                            │   • 重绘: 读 Message
    │                 │                         │                            │   • 追加: 读 Event
```

在 [`internal/runtime/stream_response.go:120-134`](file:///Users/yuqing/Documents/workspace/pigo/internal/runtime/stream_response.go#L120-L134) 的核心运行时中：
```go
case provider.StreamTextEvent:
    backfill(e.Partial) // 回填累积态
    if err := emit(ctx, agentcore.MessageUpdateEvent{
        Message:               e.Partial, // 快照
        AssistantMessageEvent: e,         // 增量
    }); err != nil {
        return agentcore.AssistantMessage{}, err
    }
```
运行时在单一安全点完成状态回填，并保证事件广播出去时，快照与增量具有绝对的因果一致性（Causal Consistency）。

## 五、设计哲学与工程启示

1. **单点拼装，多点受益（Assemble Once, Benefit Everywhere）**：
   状态拼装（将流式碎片重组成完整的消息结构）是所有消费端的共性诉求，但也是最容易写出 Bug 的环节。`pigo` 将这个复杂度完全收敛在 `runtime` 核心，不将拼装负担泄漏给上层 UI 或插件，极大地降低了端侧开发的门槛。

2. **保留底层上下文（Preserve Underlying Context）**：
   在架构设计中，抽象层往往会因为过度封装而把底层信息“抹平”。`MessageUpdateEvent` 通过包含 `AssistantMessageEvent any` 留出了一个极其重要的逃生通道（Escape Hatch），使得有高阶定制需求的调用方依然能够探查到最底层的细粒度状态。

3. **同时拥抱响应式与流式（Embrace both Reactive & Streaming）**：
   现代软件界面正在全面转向声明式状态驱动（State-driven UI），而通信传输层则是事件驱动（Event-driven Streaming）。双轨模型桥接了这两种完全不同的编程范式，使得同一份事件流能够无缝服务于命令式 CLI、流式 Web 管道与声明式 TUI。
