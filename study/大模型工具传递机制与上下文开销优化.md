## 一、核心结论：每一次请求都必须全量传递

在现有的主流商业与开源大模型接口规范（如 OpenAI Chat Completions、Anthropic Messages API、DeepSeek 等）中：
> **每一次向模型端发起的 HTTP 请求，都必须完整携带当前可用的全部工具定义（Tools 数组）。**

即使是一次长达 20 轮的多轮交互，第 20 次请求也必须像第 1 次一样，将所有工具的名称、描述以及参数 JSON Schema 全量打包在请求体中。

## 二、底层机制：LLM API 的完全无状态（Stateless）特性

大模型服务端的推理引擎本身是**完全无状态的（Stateless）**：
1. 服务端不会在内存或连接会话中为客户端保持“该客户端注册了哪些工具”的状态；
2. 模型在自回归预测下一个 Token 时，需要依据当前请求上下文推断是否需要触发函数调用（Function Calling）；
3. 因此，每次发起的 HTTP 请求必须是**完全自包含（Self-contained）**的 Payload：

```json
{
  "model": "claude-3-5-sonnet",
  "system": "你是一个代码助手...",
  "messages": [
    {"role": "user", "content": "帮我看看 main.go"},
    {"role": "assistant", "tool_calls": [...]},
    {"role": "tool", "content": "..."}
  ],
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "read",
        "description": "Read file contents...",
        "parameters": { ... }
      }
    },
    {
      "type": "function",
      "function": {
        "name": "bash",
        "description": "Run shell commands...",
        "parameters": { ... }
      }
    }
  ]
}
```

在 [`internal/provider/providers.go`](file:///Users/yuqing/Documents/workspace/pigo/internal/provider/providers.go#L133-L135) 中，序列化逻辑直接印证了这一点：
```go
// 每次组装发送给大模型的 JSON 时，均实时从当前 Context.Tools 编码
if tools := encodeOpenAITools(req.Context.Tools); len(tools) > 0 {
    body["tools"] = tools
}
```

## 三、成本考量：工具定义如何占用 Token 与费用

工具定义并不是“免费的元数据”，而是**计入输入 Token（Input Tokens）并计费的**：
- **Schema 文本化**：服务商底层会将工具的 `name`、`description` 和 `parameters`（JSON Schema）转译成特殊的格式（例如类似 TypeScript 类型定义的文本）拼接至 Prompt 前部；
- **窗口占用**：一个定义完善的工具通常占用 100 ~ 300 个 Token。如果一个 Agent 挂载了 15 ~ 20 个工具，光是工具定义本身就会吃掉 **2,000 ~ 5,000 个输入 Token**；
- **重复累积**：在 20 轮对话中，如果没有任何缓存优化，同样的 5,000 Token 工具定义将被传输并计费 20 次，成本与网络传输开销显著放大。

## 四、工程优化策略（pigo 与业界最佳实践）

为了化解“每次必须传递”与“高昂 Token 成本”之间的矛盾，`pigo` 与现代 Agent 采用了三级优化：

### 1. 服务端前缀缓存（Prompt Caching）
这是近年来大模型提供商（Anthropic、DeepSeek、OpenAI）提供的重大架构突破：
- **机制**：服务商对请求的前缀内容（Prefix）进行哈希缓存。在构建请求时，将相对固定的 `System Prompt` 与 `Tools 定义` 放在最前面，变动的多轮对话消息放在后面；
- **收益**：从第二轮请求开始，重复传递的工具定义会被服务商的显存/KV Cache 命中（Cache Hit），**费用通常直降 50% ~ 90%**，并且首字延迟（TTFT）大幅缩短。

### 2. 渐进式披露（Progressive Disclosure：核心工具 + 技能按需加载）
如果将所有可能用到的能力都定义为工具，不仅消耗海量 Token，还会让模型在过多的选择中出现“选择困难（Tool Selection Degradation）”。

`pigo` 采用了**渐进式披露**的设计：
- **常驻工具轻量化**：核心工具集严格保持精简（仅内置 `read`, `write`, `edit`, `grep`, `find`, `bash` 等基础能力）；
- **技能（Skills）不作为常驻 Tool**：用户定义的数十个复杂技能（`SKILL.md`）**不注册为工具 Schema**，而仅仅是在系统提示词里注入极简的说明行（名称与一句话描述）；
- **动态按需拉取**：当大模型认为当前任务需要用到某项技能时，模型自主调用常驻的 `read` 工具去读取对应的 `SKILL.md` 正文。这使得成百上千项专业技能不会增加每次请求的默认工具体积。

### 3. 结构性策略裁剪（Tool Policy）
通过命令行参数 `--allowed-tools` / `--disallowed-tools` / `--no-tools`：
- 在环境装配期通过 [`ApplyToolPolicy`](file:///Users/yuqing/Documents/workspace/pigo/internal/cli/run/toolpolicy.go#L170-L185) 物理剔除当前场景无需使用的工具；
- 被剔除的工具不仅不能被调用，而且**不会被序列化进 `tools` 数组**，从而完全不占用网络带宽与上下文窗口。
